## 1. 文档目的

本交接文档的目标不是简单罗列目录和文件名，而是以完整、可接续、可验证的方式，说明 ChainSight 项目的业务定位、系统边界、三套版本的关系、原始代码存在的问题、重构版做了哪些关键调整、当前测试验证到了什么程度、后续还应当如何继续推进。接手人员阅读本文件后，应能够回答三个核心问题：其一，系统每天如何运行；其二，各版本应如何选用；其三，后续维护和优化应从哪里入手。

## 2. 项目概述

ChainSight 是一套按日推进的供应链仿真系统。系统在每一个仿真日中，会围绕客户需求、生产能力、网络调拨、物流执行和净需求回推五个核心主题进行计算，并通过统一的全局状态中枢将结果在模块之间持续传递。若用业务语言概括，该系统每天都在回答这样一组问题：今天客户真正提出了什么需求，现有库存能满足多少，工厂今天能生产多少，网络中的节点之间应如何调拨，物流能否真正把这些调拨发出去，以及在所有动作执行之后，整个网络到底还缺什么。

项目当前存在三种工程形态。第一种是 `ChainSight_Dev` 原始版，它是最早形成完整业务口径的基础实现，也是所有重构与优化工作的结果对照基线。第二种是 `src` 本地重构版，它在不改变核心业务规则的前提下，对主流程、模块边界、状态管理、续跑能力和性能瓶颈进行了系统梳理，是当前最适合继续开发和维护的版本。第三种是 `pgsql_db` 数据库版，它并未重新发明算法，而是在 `src` 标准仿真内核的外围增加了数据库初始化、配置读库、结果落库和汇总生成等企业交付能力，用于支撑集中化、可审计和可追溯的运行场景。

## 3. 三个版本的定位与关系

### 3.1 Dev 原始版

`ChainSight_Dev` 版本保留了最完整、最原生的业务表达方式。它的最大价值不在于工程结构，而在于它提供了一套经过长期业务沉淀的规则实现，使得后续任何重构和优化都能有明确的比对对象。从交接角度看，Dev 原始版更像一套业务答案库，适合用于追溯历史逻辑、比对结果差异、核实规则来源。其不足也十分明显，即单文件偏大、职责耦合严重、跨模块状态依赖隐式且难以阅读，不宜再作为主开发分支继续扩展。

### 3.2 `src` 本地重构版

`src` 重构版是当前推荐的开发主线。该版本并没有改变 M1、M3、M4、M5、M6 的业务顺序，也没有重写一套新的算法内核，而是把原先分散在大文件中的逻辑拆解为更明确的分层结构。入口由根目录 `run.py` 统一接收命令行参数，真正的模式分发位于 `src/core/run/` 子包，主日循环位于 `src/core/main_integration/` 子包，共享状态则集中收口到 `src/core/orchestrator/` 子包。模块侧的导入统一通过子包进行（`from src.modules import demand_planning`），向后兼容通过 `src/modules/__init__.py` 中的别名实现（`module1 = demand_planning`）。原有的 `module1.py`~`module6.py` 薄包装层文件已在 v2.0 合并重构中全部删除，`module6.py` 的 1547 行核心逻辑已拆分为 `logistics_execution/` 子包下 8 个子模块。此外，v2.0 新增了 `src/config/` 集中化配置管理和 `src/utils/normalization.py` 统一标识符规范化，进一步消除了各模块间的重复实现。

### 3.3 `pgsql_db` 数据库版

数据库版的定位应当被理解为“标准仿真内核的数据库适配层”，而不是“另一套新的仿真系统”。其核心工作包括建立或检查 PostgreSQL 数据库、将 Excel 配置导入统一的 `cfg_*` 表、按照 `config_name` 读取配置、调用 `src` 的标准仿真流程完成计算、再将结果写入 `module*_output_*`、`orchestrator_*` 与 `summary_output_*` 等标准表中。数据库版的直接价值在于，它使配置、运行批次和结果归档全部具备了集中存储、统一查询和批次隔离能力，非常适合测试环境、实施环境和生产化场景。

### 3.4 三个版本的使用建议

从交接后的实际工作出发，建议将三套版本明确区分用途。`ChainSight_Dev` 主要用于结果口径回归和历史逻辑核对；`src` 应作为后续开发、调试、问题定位和功能扩展的主要工作分支；`pgsql_db` 则应作为需要集中化管理、结果落库、审计追踪和批量运行时的标准交付方式。若团队在后续工作中没有明确区分三者的职责，很容易出现“拿 Dev 当主开发代码”或“把 DB 版误当成另一套算法”的理解偏差，从而增加不必要的维护成本。

## 4. 原始代码评估

原始代码并非没有价值，相反，它是整个 ChainSight 项目能够稳定沉淀业务规则的前提。M1 到 M6 的顺序、主要数据口径、核心输出格式以及大部分历史回归结果，都是从原始版中稳定生长出来的。因此，在任何工程评价之前，应先肯定原始版在业务落地和规则沉淀上的意义。

但从长期维护角度看，原始版的问题也非常集中。首先，多个模块同时承担了配置读取、数据清洗、业务计算和结果输出，导致文件长度过大、阅读路径冗长，修改者往往需要在一个文件中跨越多个逻辑层才能定位真正的变化点。其次，跨模块状态依赖更多依靠隐式约定，例如上一个步骤是否恰好把某个字段准备成了指定格式，而不是通过显式接口和统一状态对象来表达。这使新人很难快速建立对系统运行链路的稳定理解。再次，标识符口径不统一的问题在原始版中较为常见，特别是 `material`、`location`、`sending` 和 `receiving` 字段，容易出现字符串、数值和带小数后缀混用的情况，从而在 merge、join 和 groupby 环节产生隐蔽错误。最后，原始版高度依赖文件中转，很多中间结果需要频繁写入文件、再从文件回读，这不仅增加了运行耗时，也使续跑、审计和问题重演的成本大幅上升。

综合判断，原始版最适合作为业务结果基线，而不适合作为未来的主维护形态。重构工作的必要性，不是为了让代码“更好看”，而是为了让系统具备可理解、可恢复、可验证和可扩展的工程能力。

## 5. 重构工作的总体原则

本次重构工作的第一原则是结果一致性优先。任何结构调整、性能优化、数据通道切换和数据库适配，都必须以 Dev 原始版的回归结果为准绳。第二原则是兼容优先，即尽量保留对外接口和模块入口名称，避免已有脚本和调用方式完全失效。第三原则是状态显式化优先，将库存、在途、开放调拨、生产收货、交付收货和关键日志统一交由 Orchestrator 管理，减少跨模块靠文件临时拼接状态的隐式约定。第四原则是先减低不必要的 I/O，再做计算层面的优化，避免在文件读写成本很高的前提下盲目追求局部算法加速。

## 6. 重构后的总体架构变化

重构之后，系统整体结构已经从”若干大文件串起来的业务实现”演进为”分层明确、状态集中、模块边界清晰的工程体系”。`src/core` 负责程序入口、参数处理、主日循环、状态恢复、运行目录管理和结果总结；`src/config` 负责集中化配置管理（v2.0 新增）；`src/modules` 负责 M1、M3、M4、M5、M6 各模块的业务算法；`src/utils` 提供标识符规范化、日期处理、日志、校验、时间管理和库存平衡检查等基础能力；`src/services` 负责总结报告和性能分析；`pgsql_db` 则承担数据库初始化、配置导入、读库装配与写库汇总功能。

这其中最关键的工程变化，在于 Orchestrator 成为了系统状态的统一中枢。过去分散在各模块中的库存、在途、开放调拨和 GR 信息，如今都可以在一个统一的对象中被读取、更新、落盘和恢复。这样一来，跨模块的数据流转不再依赖“这个文件里刚好存了什么”，而变成了“全局状态中当前有哪些已确认事实”。这对接手人员来说非常重要，因为理解系统的最佳方式不再是硬读所有模块源码，而是先理解状态，再理解状态如何在每天的主循环中被逐步修改。

## 7. 本地重构版运行链路说明

本地重构版的执行入口是根目录 `run.py`。程序启动后，`src/core/run/` 子包负责解析命令行参数，判断本次是本地模式还是数据库模式，并创建或选择输出目录。如果是本地模式，则主流程进入 `src/core/main_integration.py::run_integrated_simulation(...)`。该函数会先读取配置、执行预校验、判断是否具备续跑条件、在必要时恢复历史状态，然后进入真正的按日仿真循环。

在每一个仿真日内，系统先保存期初库存，再执行超期开放调拨清理和到货入库处理，然后依次执行 M1、M4、M5、M6、M3 五个业务模块。之所以是这个顺序，是因为系统先要看到客户需求和现有发货情况，再决定生产，再决定网络调拨，再决定物流执行，最后基于当日执行后的全局状态去重新计算净需求。每个模块执行结束后，其关键结果都会立即回写 Orchestrator，确保后续模块看到的是“刚刚更新过的真实状态”，而不是上一天或旧文件中的残留视图。到了日末，系统会保存期末库存与全量状态 CSV，并在整个期间结束后执行库存平衡校验和汇总报告生成。

## 8. 各模块交接说明

### 8.1 M1 需求规划

M1 的职责可以概括为“把周度预测和订单规则转换成当天真正发生的订单与发货”。在重构版中，M1 已经被拆解为配置加载、预测准备、订单生成、预测消耗、发货模拟和输出整理等多个职责单元。对接手人员而言，最重要的入口是 `run_daily_order_generation(...)`。该函数先读取和校验 M1 相关配置，再生成两类日预测视图，一类用于订单逻辑，一类用于供需日志逻辑；随后依据 AO 配置和订单日历生成订单，并消耗对应的预测；最后结合 Orchestrator 中的真实可用库存模拟今天实际可以发出的数量，并分别形成订单日志、发货日志、缺货日志和供需日志。

M1 的重构价值在于，它把“需求生成”和“库存满足”这两件原本混在一起的事情分开了。这样一来，若后续出现订单数量异常，可以先查订单生成逻辑；若发货数量异常，则可以单独追踪库存和发货模拟逻辑，不再需要在一个超大函数中反复切换上下文。

### 8.2 M3 净需求与 MRP

M3 在业务上的职责，是在综合考虑现有库存、在途供给、生产入库、安全库存和上游传播需求后，计算网络在当天的真实缺口。重构后的 M3 将网络分层、提前期计算、供需汇总和 gap 传播拆成了独立职责单元。其中，`assign_location_layers(...)` 用于根据 `(material, location)` 建立网络层级，`determine_lead_time(...)` 用于计算节点之间的计划窗口，而 `calculate_daily_net_demand(...)` 则是最核心的净需求计算函数。

在交接中必须特别强调的一点是，多物料共地点场景下，M3 层级映射的键已经统一修复为 `(material, location)`。这一修复的意义并非细枝末节，而是直接关系到层级传播是否会把不同物料的需求意外混到一起。该问题一旦处理不当，M3 与 M5 的结果都会同时出现偏差，因此后续如再调整相关逻辑，必须优先保持这一主键契约不变。

### 8.3 M4 生产计划

M4 负责把上一个仿真阶段得到的净需求转换为可执行的生产计划。其业务难点并不在于把缺口简单变成生产数量，而在于同时满足产线、换产、可靠率和跨天状态连续性等约束。重构之后，M4 已经形成了较清晰的处理阶段：首先从前一天的 `Module3Output` 中读取 layer=0 净需求；然后通过 `build_unconstrained_plan_for_single_day(...)` 构建理想计划；再通过 `centralized_capacity_allocation_with_changeover(...)` 在真实产能和换产约束下压缩和重排；接着用 `simulate_production(...)` 依据生产可靠率生成实际产出；最后将生产计划、超额记录、校验结果和换产日志写入标准输出文件，并把日末产线状态和已占产能状态保存下来，供下一天接续使用。

M4 的交接重点在于理解“计划”和“实际”的区别。`uncon_planned_qty` 只是理想需求，`con_planned_qty` 才是约束后的可生产量，而 `produced_qty` 则是叠加生产可靠率后真正可入库的量。这三层口径必须明确区分，否则很容易在排查差异时把不同阶段的数据混为一谈。

### 8.4 M5 部署规划

M5 负责在多层级网络内回答“今天应该从哪里向哪里调拨多少货”的问题，是整个系统中逻辑复杂度和维护难度最高的模块之一。重构之后，M5 的主入口 `main(...)` 会先装配来自 M1、M4 和 Orchestrator 的输入，再建立需求、库存、网络、LeadTime、DeployConfig 等缓存和索引，随后按层级逐步处理节点需求。对于每个节点，系统会先收集 SDL、安全库存、订单以及上游传播的 gap，然后依次应用 MOQ/RV 规则、优先级库存分配、pipeline supply 覆盖和 gap 向上游传递逻辑，最终形成部署计划与未满足记录。在每日主逻辑结束后，M5 还会继续执行 push / soft-push 分配以及接收空间约束裁剪，并滚动更新自己的库存日志。

M5 的交接重点有两点。第一，部署计划并不是简单由净需求直接生成，而是经过库存分配、未来在途覆盖、未来生产覆盖以及上游传播等多轮处理后形成的结果。第二，M5 生成的 `DeploymentPlan` 在进入 Orchestrator 之前会经过稳定排序和 UID 建模，这一点直接关系到后续 M6 发运与数据库对账时是否还能稳定关联同一条部署记录。

### 8.5 M6 物流执行

M6 的职责，是把已经形成的部署计划变成真正的物流发运行为。其主入口 `run_daily_physical_flow(...)` 会先装配 OpenDeployment、Truck 配置、MDQ 规则、运力计划和物料体积重量参数，再进行配置校验、重复键清理和标准化处理。随后，M6 会把尚未发完的部署记录整理成待处理需求，按路线和车型逐步判断是否满足发车条件，并通过 `VehiclePacker` 进行装车。若满足触发条件，则生成车辆日志、交付计划以及绕过规则命中日志，并根据 LeadTime 和延迟分布计算到货日期。

M6 的交接重点在于理解“计划调拨”和“真实发运”之间的差异。M5 的 `DeploymentPlan` 表示的是应当调拨的意图，而 M6 的 `DeliveryPlan` 才表示今天实际发出了什么。只有 M6 结果回写到 Orchestrator 后，发送地库存、开放调拨状态、在途记录和收货记录才会真正发生变化。也正因为如此，M6 是整个系统中最容易因为顺序或 UID 处理不当而引发连锁偏差的模块。

## 9. 数据库版说明

数据库版并不改变本地重构版的模块顺序和核心算法。其真正不同之处在于输入输出介质由 Excel 与本地文件系统切换为 PostgreSQL。程序在 `--use-db` 模式下启动时，会先由 `DatabaseInitializer.initialize(...)` 检查数据库是否存在以及配置是否已导入；如配置尚未存在，则可自动从 Excel 导入统一的 `cfg_*` 表。随后，`_load_config_from_database(...)` 会按 `config_name` 从这些统一配置表中恢复出标准的 `config_dict`。仿真完成后，`ModuleDataWriter.write_module_results_from_dict(...)` 会直接将 M1 至 M6 的内存结果写入 `module*_output_*` 表，并按 `run_id` 为本次运行建立隔离；接着，`write_orchestrator_data(...)` 会把状态 CSV 写成 `orchestrator_*` 表；最后，`generate_summary_reports_from_db(...)` 会从数据库中的模块输出表直接生成 `summary_output_*` 汇总表。

数据库版在实施中的价值是非常明确的。它使配置版本、运行批次和输出结果具备了统一管理能力，也使跨配置比对、审计追踪和批量运行变得更加自然。同时，它仍然坚持“先保证和 Dev 结果一致，再谈更激进的性能引擎”，因此当前数据库模式默认仍走标准仿真链路，这是为了最大限度降低交付风险。

## 10. 测试验证结果

本次交接所采用的测试验证，覆盖了 BC 与 OC 两类代表性配置。BC 场景使用 `BC_S5.xlsx`，仿真日期范围为 2025-10-05 至 2025-12-30，共 87 天。测试结果显示，Dev、`src` 和 DB 三个版本在 16 张核心输出表上的比对结果全部通过。性能方面，Dev 耗时 9540 秒，`src` 耗时 2897 秒，DB 模式耗时 1563 秒，对应提速分别为 3.29 倍和 6.10 倍。

OC 场景使用 `OC_Paste_S1_20251224.xlsx`，仿真日期范围为 2025-12-15 至 2026-02-28，共 76 天。测试结果同样表明，三版本在 16 张核心输出表上的结果全部通过。性能方面，Dev 耗时 97611 秒，`src` 耗时 14854 秒，DB 模式耗时 7850 秒，对应提速分别达到 6.57 倍和 12.43 倍。

从交接角度看，这组验证结果的意义不只是“跑得更快”，而是证明了重构与数据库化在结果一致性方面已经具备稳定依据。也就是说，当前系统已经完成了从“原始可用”到“工程可维护且结果可证明”的关键跃迁。

## 11. 关键变更点与重点修复

本次重构与优化过程中，最关键的变更点主要集中在状态中枢化、标识符标准化、续跑能力、稳定 UID、复杂模块拆分和数据库适配六个方向。其一，Orchestrator 统一管理库存、开放调拨、在途、GR 和关键日志，使跨模块状态不再依赖零散文件。其二，`material`、`location`、`sending`、`receiving` 等标识符统一做标准化，降低因格式不一致引起的 join 差异。其三，通过 `detect_last_complete_date(...)`、`check_resume_capability(...)` 和 `restore_orchestrator_state(...)`，系统具备了明确的续跑与状态恢复能力。其四，M5 与 M6 相关记录在进入状态与物流阶段之前都经过稳定排序和稳定 UID 处理，减少了结果顺序变化导致的连锁差异。其五，M1、M3、M4、M5、M6 均已从“大文件集中处理”变为“子模块拆分 + 兼容入口”结构。其六，数据库版形成了从 `cfg_*` 表读配置、以 `run_id` 写结果、再从数据库生成 summary 的完整闭环。

其中最值得反复强调的两处修复分别是 `(material, location)` 键修复和部署 UID 稳定化修复。前者解决了多物料共地点网络下的层级错配问题，后者解决了相同输入下因处理顺序漂移而导致 UID 不稳定的问题。这两处虽然看似细节，却都直接关系到长周期回归是否能够稳定通过。

## 12. 接手后的建议工作方式

接手团队进入项目后，建议首先以 `src` 版本作为主开发基础，不直接在 `ChainSight_Dev` 上开展新增开发。Dev 原始版应被视为结果基线和历史逻辑对照库，而不是日常修改主线。日常开发时，应优先通过短日期窗口做 smoke test，在确认主要链路无差异后，再使用 BC 或 OC 全周期配置进行完整回归。

在问题定位时，应尽量避免一开始就大范围猜测性能或算法问题，而是先确认是哪个阶段的输出开始偏离。例如，如果 M6 结果有差异，就应先查 M5 生成的 `DeploymentPlan` 是否已经偏了；若 M5 正常，再查 M6 的车型触发、旁路规则和 UID 去重路径。如果 M3 出现差异，则应先核对 Orchestrator 中的库存、在途和 GR 是否已在当日正确回写。沿着主时序逐层向后追，而不是从终态倒推所有模块，是当前最稳妥的排障方法。

同时，后续维护应统一遵守注释交接约定。`src` 与 `pgsql_db` 中的重构代码应以全中文模块注释、函数 docstring 和关键实现说明为默认标准，注释内容重点解释职责边界、输入输出口径与与 Dev 基线的一致性约束；`ChainSight_Dev` 保留为结果回归与历史逻辑基线，不要求为其补齐中文注释，避免对原始对照代码造成无关噪声。若后续出现英文注释，应优先在不改动业务逻辑的前提下翻译为专业中文注释，并同步更新交接文档中的职责说明。

## 13. 后续建议与计划

从架构治理角度看，后续最值得持续推进的事项包括：继续将 M6 中仍偏大的主流程文件进一步拆小；为核心模块补更明确的输入输出契约，降低 DataFrame 隐式列依赖；将 Dev、`src` 与 DB 三版本的自动回归对比纳入持续集成；以及为数据库模式增加更明确的运行状态表、失败状态表和 resume 机制。从算法治理角度看，M3 与 M5 仍是最值得继续优化的重点模块，因为它们既有较高的计算密度，也有较高的业务影响面。所有后续优化都应优先采用可回滚、可开关、可对比的方式推进，并保留 Dev 对照能力。

若以 30/60/90 天来安排后续接手计划，则 30 天内建议完成环境固化、运行手册复核、短窗口 smoke test 和 BC/OC 回归脚本的复跑；60 天内建议完成 DB 模式运行监控、异常重试策略、模块 contract 初稿和交接材料补录；90 天内建议完成模块级自动对比、DB resume 方案设计和 M6 的二次拆分设计稿。这样的节奏既能保证项目平稳接手，也有利于逐步降低后续维护成本。

## 14. 结论

ChainSight 当前最重要的成果，不是单纯把程序从“能跑”提升到“跑得更快”，而是在不破坏既有业务结果的前提下，把系统改造成了可理解、可恢复、可扩展、可落库、可审计的一套工程体系。对于接手团队而言，最稳妥的后续策略是以 `src` 作为开发基线，以 Dev 作为结果基线，以 DB 模式作为实施和生产化交付基线。只要能够持续守住主流程顺序、关键状态主键和输出契约三条底线，ChainSight 后续的维护与迭代将明显比原始阶段更加可控。

## 16. 文件格式速查

系统每日输出的标准文件格式已经相对稳定。M1 输出 `module1_output_YYYYMMDD.xlsx`，包含 `OrderLog`、`ShipmentLog`、`CutLog`、`SupplyDemandLog` 和 `Summary`。M3 输出 `Module3Output_YYYYMMDD.xlsx`，核心为 `NetDemand`。M4 输出 `Module4Output_YYYYMMDD.xlsx`，包含 `ProductionPlan`、`CapacityExceed`、`Validation` 和 `ChangeoverLog`。M5 输出 `Module5Output_YYYYMMDD.xlsx`，包含 `DeploymentPlan`、`UnfulfilledLog`、`StockOnHandLog` 和 `Validation`。M6 输出 `Module6Output_YYYYMMDD.xlsx`，包含 `DeliveryPlan`、`VehicleLog`、`TruckUsageLog`、`UnsatisfiedMDQLog`、`ValidationLog` 和 `BypassRuleHitLog`。

除模块输出外，Orchestrator 每日还会输出 `unrestricted_inventory_YYYYMMDD.csv`、`open_deployment_YYYYMMDD.csv`、`planning_intransit_YYYYMMDD.csv`、`space_quota_YYYYMMDD.csv`、`production_plan_backlog_YYYYMMDD.csv`、`production_gr_YYYYMMDD.csv`、`delivery_gr_YYYYMMDD.csv`、`shipment_log_YYYYMMDD.csv`、`delivery_shipment_log_YYYYMMDD.csv`、`inventory_change_log_YYYYMMDD.csv` 和 `daily_logs_YYYYMMDD.csv`。数据库模式下，对应配置表统一使用 `cfg_*` 前缀，模块输出表统一使用 `module*_output_*` 前缀，状态表统一使用 `orchestrator_*` 前缀，汇总表统一使用 `summary_output_*` 前缀，所有运行批次通过 `run_id` 隔离。

## 17. v2.0 合并重构变更说明（2026-04-06）

v2.0 合并重构在不改变业务逻辑的前提下，完成了以下六项工程治理工作：

### 17.1 module6.py 拆分

原 `src/modules/module6.py`（1547 行）的核心物流执行逻辑已拆分为 `logistics_execution/` 子包下的 8 个子模块：`constants.py`、`initializer.py`、`data_preparer.py`、`simulation_engine.py`、`route_processor.py`、`constraint_enforcer.py`、`output_builder.py`、`main.py`。拆分后每个文件职责单一，便于定位和维护。

### 17.2 shim 文件删除与导入统一

`module1.py`、`module3.py`、`module4.py`、`module5.py`、`module6.py` 五个薄包装层文件已全部删除。所有导入统一通过子包进行，向后兼容通过 `src/modules/__init__.py` 中的别名实现：

```python
from . import demand_planning
module1 = demand_planning  # 向后兼容
```

core 层调用文件（`simulation_file.py`、`simulation_db.py`、`production_planning_runner.py`）已同步更新为从子包导入。

### 17.3 config.yaml 集中化配置管理

新增 `src/config/` 模块（`__init__.py`、`loader.py`、`default_config.yaml`），将各模块 `constants.py` 中分散的可配参数（如 `DEFAULT_MOQ`、`DEFAULT_RV`、`DEFAULT_PTF`、`DEFAULT_LSK`、`DEFAULT_CHANGEOVER_TIME`、`DEFAULT_LEAD_TIME`、`PUSH_LEVELS` 等）集中到 `default_config.yaml` 中统一管理。各模块 `constants.py` 改为从 config 读取，导出接口不变，下游代码无需修改。支持通过 `CHAINSIGHT_CONFIG` 环境变量指定自定义配置文件覆盖默认值。

### 17.4 标识符规范化统一

新增 `src/utils/normalization.py`，统一替代 6-7 处重复的 `normalize_location`、`normalize_material`、`normalize_identifiers` 实现。该模块支持 `material`、`from_material`、`to_material`、`location`、`dps_location`、`sending`、`receiving`、`sourcing`、`line`、`delegate_line`、`changeover_id` 共 11 个标识符列的规范化。各模块原有文件改为 re-export 薄代理层，保持所有下游导入路径不变。

### 17.5 日期辅助函数

新增 `src/utils/date_helpers.py`，提供 `convert_date_column`、`convert_date_columns`、`ensure_date_format`、`format_date`、`format_date_for_file`、`parse_date` 等纯函数，整合各模块中重复的日期处理逻辑。

### 17.6 死代码清理

删除以下零引用文件：
- **core 层**：`src/core/main_integration.py`（2610 行）、`src/core/orchestrator.py`（1512 行）、`src/core/parallel_executor.py`（338 行）、`src/core/run.py`（1406 行）——这些单体文件对应的子包已包含全部功能
- **utils 层**：`simulation_cache.py`、`performance.py`、`parallel_optimizer.py`、`process_pool_executor.py`、`high_perf_executor.py`、`multiprocess_executor.py`——经确认零引用

所有删除文件已归档至 legacy 分支，可按需恢复。

### 17.7 严格约束

整个 v2.0 合并重构过程中，`ChainSight_Dev/` 目录下未做任何修改，确保结果回归基线不受影响。
