# 中文注释规范与维护约定

## 1. 目的

本文件用于统一 `src/` 与 `pgsql_db/` 重构代码的中文注释标准，确保后续维护人员在阅读、交接、扩展与回归比对时，能够快速理解职责边界、输入输出口径与关键兼容约束。

## 2. 适用范围

- 适用目录：`src/`、`pgsql_db/`
- 不适用目录：`ChainSight_Dev/`
- 不适用内容：业务数据、运行日志、数据库字段名、文件名、工作表名、代码标识符本身

说明：`ChainSight_Dev/` 作为历史实现与结果回归基线，原则上不因注释规范化而引入额外改动，以免影响基线对照。

## 3. 基本原则

- 注释优先解释“为什么这样做”“输入输出是什么”“与哪条基线保持一致”，避免重复描述显而易见的代码动作。
- 注释默认使用专业中文表达；技术专有名词、稳定标识符、库名与表名可以保留原文。
- `Module1` ~ `Module6` 作为项目内稳定模块名称，注释中保留 `Module` 命名，不强制翻译。
- 不得借“补注释”顺带修改业务逻辑、参数口径、字段映射、执行顺序或异常处理策略。
- 若注释与代码行为不一致，优先修正注释；除非单独需求明确要求，否则不通过本类任务改逻辑。

## 4. 模块级注释要求

每个重构后的主文件或拆分子文件，建议在文件头部补充模块 docstring，至少说明以下三项：

- 文件职责：该文件在整体链路中承担什么角色
- 调用位置：通常由哪个入口、哪个模块或哪个批次流程调用
- 兼容约束：与 Dev 基线、数据库模式、续跑能力或下游接口相关的关键约束

推荐模板：

```python
"""文件功能名称。

职责：
- 说明本文件负责的核心能力。
- 说明与上下游模块的衔接关系。
- 说明必须保持不变的兼容性约束。
"""
```

## 5. 函数级注释要求

公共函数、主流程函数、复杂辅助函数应具备中文 docstring。建议至少包含：

- 功能概述
- 参数说明
- 返回说明
- 必要时补充副作用、边界口径或基线一致性说明

推荐模板：

```python
def example(arg1, arg2):
    """一句话说明函数用途。

    参数：
        arg1: 参数一的业务含义。
        arg2: 参数二的业务含义。

    返回：
        返回值的结构与业务口径说明。
    """
```

## 6. 行内注释要求

- 行内注释只用于解释非直观逻辑、兼容性处理、性能优化分支或基线对齐原因。
- 能通过函数名、变量名或上下文直接看懂的语句，不额外添加解释性注释。
- 行内注释优先解释“原因”，例如：
  - 为什么不能排序
  - 为什么要保留某个字段
  - 为什么数据库模式与本地模式必须使用同一口径

推荐写法：

- `# 与 Dev 基线版本保持一致，不在此处重置随机种子`
- `# 先过滤当前仿真日，避免累计结果重复写入当日表`
- `# 使用稳定排序保证 UID 生成顺序可复现`

不推荐写法：

- `# 设置变量`
- `# 循环处理数据`
- `# 调用函数`

## 7. 英文保留与翻译规则

### 7.1 必须翻译为中文的内容

- 纯英文说明句
- `Args:`、`Returns:`、`Notes:`、`Example:` 等模板标签
- `Try to import...`、`Check if...`、`Original implementation...` 这类实现说明

### 7.2 可以保留英文的内容

- 库名、框架名、数据库名，如 `DuckDB`、`Pandas`、`PostgreSQL`
- 配置表名、输出表名、工作表名、字段名，如 `OrderLog`、`SupplyDemandLog`
- 类型检查或静态分析指令，如 `# type: ignore[...]`
- SQL 关键字、正则表达式片段、日期格式字符串

### 7.3 推荐写法

- 推荐：`# 基于 Pandas 的回退方案`
- 推荐：以“`SupplyDemandLog` 必需列”这类方式描述稳定标识符
- 推荐：`# 使用 DuckDB 批量优化路径`

## 8. 与 Dev 基线的关系说明

- `ChainSight_Dev/` 不作为中文注释补齐对象。
- 当重构代码中需要引用 Dev 基线行为时，推荐写法为：
  - `与 Dev 基线版本保持一致`
  - `按 Dev 基线版本口径处理`
  - `避免偏离 Dev 基线输出`

## 9. 维护流程建议

后续新增或重构文件时，建议按如下流程执行：

1. 先完成功能实现或结构调整。
2. 再补模块 docstring 与关键函数 docstring。
3. 检查是否残留明显英文说明注释。
4. 如同步更新了职责边界或运行口径，必须更新对应交接文档。
5. 在提交前确认：本次变更是否只改注释，还是同时改了代码逻辑，并在提交说明中写清楚。

## 10. 交接要求

交接时，至少应同步以下材料：

- 本文件：`docs/交接文档/Refactored/中文注释规范与维护约定.md`
- 总交接文档：`docs/交接文档/Refactored/项目交接文档.md`
- Core 文档：`docs/交接文档/Refactored/core.md`

若后续团队继续拆分文件，需在交接材料中同步补充：

- 新文件职责说明
- 主调用链更新说明
- 与旧文件或旧入口的兼容关系说明

## 11. 结论

中文注释规范的目标不是“让注释变多”，而是让重构后的代码具备稳定的可阅读性、可交接性与可维护性。后续所有注释性改动都应坚持两个底线：

- 不改变业务逻辑
- 不破坏 Dev 基线与数据库交付口径
